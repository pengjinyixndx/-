# 《心跳副本》微信小程序 逆向分析报告

> 分析时间：2026-10-04 · 分析对象：用户本机正在运行的微信小程序 `wx5ef8e5d3113b6f85`
> 结论先行：**这是一款「情侣真心话大冒险」小游戏**，界面是深血红 + 奶油白的菜单式结构，
> 内置 5 个玩法模块（真心话大冒险 / 大转盘 / 骰子 / 红绿灯 / 玩法说明）+ 自定义题库。
> 本仓库根目录的 `index.html` 是它的**静态网页复刻版**。

---

## 一、我是怎么找到这个小程序的

用户只提供了一张菜单截图和一个线索：「它是个微信小程序，我已经打开并登录微信」。
顺着这个线索，从磁盘上把小程序挖了出来。

### 1. 定位微信小程序缓存

| 步骤 | 发现 |
|---|---|
| 找微信数据目录 | `C:\Users\19229\Documents\xwechat_files`（微信 4.x 新架构，不是老的 `WeChat Files`） |
| 找小程序包目录 | `%APPDATA%\Tencent\xwechat\radium\users\<hash>\applet\packages\` |
| 按修改时间排序 | 3 个包的时间戳是**当天 11:19**（正是用户打开小程序的时刻） |
| 锁定目标 | `wx5ef8e5d3113b6f85` — 唯一有 `usr/miniprogramLog`、`mmkvadapterstorage`（用户数据）的包，即**前台正在运行**的那个 |

### 2. 尝试解包 `.wxapkg`（失败，但结论明确）

网上通用的解法是：`V1MM` 头 → 首字节 XOR `0x66` → 标准 `0xBE` 包头 → 按文件表切分。

实测结果：

```
tag            : b'V1MM'          ← 头部确实是 V1MM
entropy(body)  : 7.5773           ← 极高熵
16B block 唯一率: 0.93921          ← 不是 ECB 分组加密
gzip/zlib/zstd 魔数: 均未命中
单字节 XOR 扫描 : 最高可打印率仅 73%  ← 不是简单异或
声明长度 vs 实际 : 2,983,766,053 ≠ 1,836,608  ← 头部字段也解不出来
```

对照同目录下其它 9 个小程序的包（`wx8c5b1cac43b8b944` 五子棋、`wxb2043232183dac7f` Cocos 游戏、
`wxfc4ef6d539d03373` 活动类小程序…）**全部**呈现同样的密文特征。

> **结论：微信 4.x 把 `.wxapkg` 在磁盘上整体加密了**（按包异或/流式密钥），
> 老一套「XOR 0x66 + 解包」的方法在这台机器上已经失效。
> 连 `applet.db`（SQLite）也是加密的：文件头是 `07 81 a3 5d 46 b3 9d a0`，不是 `SQLite format 3`。

### 3. 改用「侧信道」取证

代码拿不到，但小程序的**缓存资产是明文的**：

| 证据 | 内容 | 说明了什么 |
|---|---|---|
| `local/wx5ef8e5…/usr/miniprogramLog/log1` | 13KB 明文日志：`wx.getStorageSync`、`wx.setStorageSync`、`wx.onAppShow`… | 全程 **没有一次 `wx.request`** → 纯离线小程序，题库内置在本地 |
| `local/wx5ef8e5…/store/images/wx5ef8e5…` | 140×140 PNG | 应用图标：奶油白玻璃质感的「P」字图标 |
| `applet/icon/` | 只缓存了别的小程序的图标 | 该小程序可能未缓存桌面图标 |
| `codecache/25510/` | V8 `cachedata` 字节码 | 全是基础库（`WAServiceMainContext.js` 等），**不是业务代码** |
| 其它 appid 的 `usr/https/` | 五子棋的 cocos 资源明文可读 | 反证：只有业务包被加密，CDN 缓存不加密 |

### 4. 动态内存取证（成功，且拿到了官方文案）

静态三层全加密之后，我转向**运行时**：小程序在跑，解密后的 JS 一定在宿主进程内存里。

```
OpenProcess(PROCESS_VM_READ) → 沙箱未拦截
VirtualQueryEx 枚举 MEM_PRIVATE 可读区 → ReadProcessMemory 整段读取
→ 中文串按 UTF-8 / UTF-16LE / GBK 三种编码探针定位
```

关键锚点探测结果（`analysis/probe_encoding.py`）：

| 探针 | UTF-16LE | UTF-8 | 结论 |
|---|---|---|---|
| 真心话大冒险 | 21 处 | 5 处 | **命中，业务包就在内存里** |
| 心跳副本 | 21 | 2 | 命中 |
| 角色名称 / 玩法说明 | 5 / 5 | — | 命中 |
| 温和 / 热辣 / 猛烈 / 极限 | 21 / 10 / 10 / 10 | 8 / 4 / 4 / 5 | 命中 |

宿主进程是 **pid 120748**（583MB，内存中出现 `wx5ef8e5d3113b6f85` 共 379 次）。
从这些区域 dump 出 13 万条文本片段，其中恢复出了**小程序自己的官方文案**，
而且是一整段完整的「玩法说明」页面：

> **心跳副本是一款专为情侣设计的互动游戏合集，包含真心话大冒险、骰子、大转盘、红绿灯等多种游戏。**
>
> **心跳副本玩法说明**
> 基本玩法 / 使用步骤
> 1　「角色名称」中设置双方的昵称
> 2　选择想要玩的游戏和难度等级
> 3　按照游戏提示进行互动
>
> **会员权益**
> 开通会员后可解锁所有游戏和高级难度，获得更丰富的游戏内容体验。
>
> **隐私保护**
> 请妥善保管您的账号信息，禁止将游戏内容用于非法用途。
>
> 祝您和另一半玩得开心！

这段是**官方元数据**（不是我的推测），它证实/推翻了三件事：

1. **五个模块的构成与我的复刻完全一致** —— 描述里点名的正是
   真心话大冒险、骰子、大转盘、红绿灯；
2. 原版引导流程就是「设昵称 → 选游戏与难度 → 按提示互动」，
   与截图的「角色名称」抽屉吻合；
3. **原版确实有解锁机制，而且是「会员」** ——
   「开通会员后可解锁所有游戏和高级难度」。
   我之前加「心跳值积分解锁」时只是猜测，现在看方向对了（免费等价物），
   但**原版是付费会员制**，这一点可以确认。

原文已存为 `analysis/evidence/小程序官方文案.md`。

**但题库正文仍未拿到**：dump 出的 13 万条片段里，以全角问号结尾的句子只有 3 条
（还都是小程序推荐位的广告语）。原因很可能是：小程序被切到后台后，
深层游戏数据要么尚未加载，要么已被回收。

> 复现方法：把小程序停在**真心话大冒险的抽卡界面**再执行
> `python analysis/memdump_scan.py <out> <pid>`，此时牌堆必然驻留在内存中。

### 5. 确认它是什么产品

搜索截图里的独有词组合「温和 / 热辣 / 猛烈 / 自定义 + 大转盘 + 骰子 + 红绿灯」，
命中了 **CoupleGame 真心话大冒险**（法国 `Action ou Vérité` 的中文化版本，
MD5 `0591516B5D917F821738999E308E3F2`，包名 `com.antoinehabert.actionverite`）。

公开资料里对它的描述与截图**逐条吻合**：

- 「默认是温和模式，在主页面点击左上角三条杠图标」→ 你截图里打开的正是这个抽屉
- 「在左侧菜单中可以看到【温和】下面还有其他模式…提供**热辣、猛烈和个性化设置**」
- 「内置多种小工具：**骰子、大转盘**、抛硬币、随机名单、卡片选择」

> 判断：这个微信小程序是 CoupleGame 的**国内小程序仿制/汉化版**，
> 但结构上做了本地化增补（多了「红绿灯」这个反应力小游戏，以及二级的「初级/高级」分层）。
> ⚠️ 无法 100% 证实两者是同一款——小程序可能只是撞了同一套玩法框架。

## 二、产品结构逆向

### 2.1 从截图直接读出的信息架构

左侧抽屉是一份完整的**玩法目录**，层级为「分组 → 模式」：

```
角色名称                    ← 顶部：玩家身份（团队图标）
────────────────────────
名字                        ← 可编辑的角色名

真心话大冒险                 ← 分组
  ♡ 温和      ← 实心心形，最细
  ♡ 热辣      ← 实心心形
  ♡ 猛烈      ← 心形带「裂纹/撕裂」描边
  ♡ 极限      ← 心形 + 放射状爆发（最"炸"）
  ♡ 自定义    ← 火焰图标（不是心形！）

大转盘                       ← 分组
  ♡ 初级
  ♡ 高级

骰子                         ← 分组
  ▣ 初级      ← 骰子图标（点数为 1）
  ▣ 高级      ← 骰子图标（点数为 5）

红绿灯                       ← 分组
  ♡ 初级
  ♡ 高级

▣ 玩法说明                   ← 独立入口
```

**最有价值的设计细节**：四档强度的图标是**同一个心形的四种"躁动程度"**——
从平滑心形 → 带尖角 → 带裂纹 → 带放射爆发。
这是一套"强度可视化"隐喻，比单纯写「温和/热辣/猛烈/极限」高级得多。
复刻版里我用 SVG path 忠实还原了这组递进关系。

### 2.2 视觉语言

从截图取色与构图：

| 维度 | 观察 |
|---|---|
| 主背景 | 深酒红 → 近黑的渐变（`#5c0920` → `#1c030b` 量级） |
| 抽屉 | 高饱和正红（`#c8103e` 量级），**不透明、覆盖式** |
| 图标/文字 | 纯白（`#fff` / 奶油白 `#fdf2e6`） |
| 分隔线 | 极细的白色半透明 1px |
| 排版 | 分组标题**低对比度**（灰白），模式名**高对比度**（纯白）；靠"明度差"建立层级而非字号 |
| 图标风格 | 面性（filled）+ 圆润，实心心形带轻微内阴影 |
| 交互暗示 | 行高约等于 2 倍字号，整行可点 |
| 状态 | 「温和」的字比选中项暗一档 → 未选中态用降透明度表示 |

背景里还能看到一个巨大的柔焦圆形/字母（截图右侧那个 "P"），
推测是**主界面的大 Logo 或转盘**，被抽屉遮挡。

### 2.3 玩法机制推断

| 模块 | 机制 | 依据 |
|---|---|---|
| 真心话大冒险 | 二选一（真心话/大冒险）→ 抽卡 → 玩家执行；四级强度分级题库 | 截图 + CoupleGame 公开玩法 |
| 自定义 | 用户自己写题，混入对应强度牌堆 | 菜单里的「自定义」+「个性化设置」描述 |
| 大转盘 | 指针停在扇区上，决定"做什么" | 截图 + 公开描述 |
| 骰子 | 掷点数映射到动作/次数 | 截图 + 公开描述 |
| 红绿灯 | 反应力小游戏（红灯等、绿灯点） | 截图；这是本地化增补项 |
| 玩法说明 | 规则页 | 截图 |
| 角色名称 | 玩家身份，影响"轮到谁" | 截图顶部 |

**变现线索**：CoupleGame 原版「切换模式时总弹付费提示」→
小程序版的四档强度很可能也是**逐步解锁/看广告解锁**的设计。
复刻版里我把它实现成「心跳值」积分解锁（抽卡 +2，红绿灯获胜 +8/+16），
保留了"分级解锁"的节奏，但去掉了广告。

## 三、复刻版实现说明

### 3.1 交付物

```
心跳副本/
├─ index.html              ← 单页入口（8 个视图）
├─ assets/
│  ├─ style.css            ← 设计系统（深血红 + 奶油玻璃 + 哥特衬线）
│  └─ app.js               ← 全部逻辑（零依赖，约 900 行）
├─ analysis/               ← 逆向取证工具与证据
│  ├─ unpack_wxapkg.py     ← wxapkg 解包器（支持 V1MM + 逐包推导 key）
│  ├─ classify_unpack.py   ← 批量识别哪些包是标准格式
│  ├─ diag_wxapkg.py       ← 加密特征诊断（熵/分组/魔数/XOR 扫描）
│  ├─ probe_encoding.py    ← 内存探针：定位业务包并判定字符串编码
│  ├─ memdump_scan.py      ← 全进程内存扫描（UTF-8 / UTF-16LE / GBK）
│  ├─ dump_bundle.py       ← 从业务包所在区段批量提取文本
│  ├─ dom-smoke.mjs        ← DOM 集成测试（21 项，全绿）
│  ├─ bank-audit.mjs       ← 题库审计（重复 / 高相似 / 同一机制扎堆）
│  └─ evidence/            ← 提取出的图标、数据库副本
└─ analysis/心跳副本-逆向分析.md   ← 本文件
```

**打开方式**：直接双击 `index.html`（纯静态、无构建、无网络请求、数据只写 localStorage）。

#### 题库：400 条，按"提问角度"而非"换词"区分

题库是本项目最费工夫、也返工最多的部分，一共写了三版。

**第一版（16 条/档，共 128 条）是失败的**：看似丰富，实际大量条目在问同一件事，
只是换了说法。例如温和层同时存在：

- 「说出你最喜欢我的三个地方」与「你最珍惜我身上哪一种不像别人的地方」
- 「我做过的哪件小事，让你偷偷高兴了很久」与「你手机相册里最近一张和我有关的照片」
- 「模仿对方最常做的一个小动作」与「学对方说话的语气，复述一句话」

大冒险更严重：温和层 20 条里有 **9 条以「说 / 讲 / 叫」开头**，抽到哪张都一个味儿。

**第二版（20 条/档，共 160 条）**改成先定框架再填内容：每条必须占一个互不重叠的
提问角度，大冒险要求动作机制各异。

**第五版（50 条/档，共 700 条，七档）是本版**。用户前后提了五条很具体的意见：

1. **尺度不够，加一档 18+**；
2. **第三档起就要强烈、大幅度的肢体接触** —— 原话是
   *「中间三个档次本质还是一致的，一直停留在表层的轻轻触碰、亲吻之类」*；
3. **把「由对方决定」这类机制全部删掉** —— 理由是实测的：
   *「双方脑子都很空，而且也说不出口」*。这条比任何设计理论都准：
   一张把决定权推回去的卡，在最需要它的那一刻必然会卡住。
4. **猛烈与极限之间再加两档过渡**；
5. **最后两档之间仍然模糊**。

于是七档按**动作机制**（而不是措辞强度）重排：

| 档位 | 动作机制 | 尺度 |
|---|---|---|
| 温和 | 说话、表演、猜测 | **零身体接触** |
| 热辣 | 耳语、对视、轻触 | 只到牵手 / 拥抱 / 额头 / 手背 |
| 猛烈 | 拉、抱、按、压、跨坐 | 大幅度肢体动作，衣物开始离开 |
| 灼热 | 收紧、锁住、夹住、悬空、压制 | 力度与贴身摩擦拉满，**仍不碰敏感部位** |
| 临界 | 隔衣按压 / 托贴 / 推移 / 指尖 / 腿 / 身体 | **隔着衣物**接触胸、大腿内侧、臀，**还不脱** |
| 极限 | 髋部、手腕压制、解开全部衣物、直接触碰 | 衣物离开，全身接触 |
| 禁区 | 进入、体位、用嘴、用手 | 18+，敏感部位用「小花园」等代称 |

这一版做了两件关键的事：

**其一，把「尺度」重新定义成机械动作的强度**，而不是形容词的强度——
这才是用户说的「第三个档次开始要强烈的肢体接触」。

**其二，回答「最后两档还是模糊」**：第 4、5 条的根因是
「隔着衣物接触敏感部位」和「脱掉衣物直接接触」被我塞进了同一档。
拆开后就清楚了：**临界 = 隔衣**，**极限 = 脱衣直接接触**，
**禁区 = 性行为本身**。这条边界写成了可执行规则（见下）。

### 工具在这一轮抓到的真问题

1. **猛烈与极限的真心话有 14 条完全重复**（扩建时复制了旧内容）；
2. **极限·大冒险有 24/50 条以「嘴唇/舌尖」起手** —— 正是用户抱怨的
   *「一直停留在表层的轻轻触碰、亲吻之类」*，而且**每一行文字都不重复**，
   单看去重是干净的。只有统计动作机制才能发现。修完降到 5/50；
3. 新增的**临界档一度 33/50 都是「按/压」** —— 同样是单一机制刷屏。
   换掉动词（描/勾/托/捧/蹭/搓/摩/夹/掐/拍）后分布变成 13/9/8/8/6/5；
4. 若干组高相似对、6 处禁用机制残留。

由此新增两条可执行规则：

- **机制单一度**：任一具名机制占比 > 40% 即报错。
  （「其他」是脚本没有标签的兜底桶，占比高只说明标签太粗，另行提示而非判错。）
- **档位边界**（`analysis/tier-boundary.mjs`）：敏感部位最早只许出现在「临界」、
  脱衣与直接接触最早只许出现在「极限」、性行为最早只许出现在「禁区」。
  700 条靠人眼守不住，所以把它变成 regex 规则。

修完是 `700 条题目全部落在各自档位的边界内` + `合计 700 条题目，0 个问题`。

这个"没有重复"不是自我感觉，而是被工具验证的：

```powershell
node analysis/bank-audit.mjs .     # 题库审计
node analysis/dom-smoke.mjs .      # 集成测试
```

`bank-audit.mjs` 用 `vm` 真实加载题库，做四件事：精确重复、规范化重复（去标点）、
**字符二元组 Jaccard 相似度 ≥ 42% 的高相似对**、以及大冒险的机制分布统计。

它在三版里各抓到过真问题：第二版抓到「9 条以『说』开头」；
第三版抓到 5 组高相似对，例如「让对方指定一个位置，你在那里留一个吻」与
「让对方选一个位置，你在那里留下一个牙印」——**换词不换机制，正是用户抱怨的那种重复**。
集成测试里也有一条硬断言：走完四档全部 400 张牌，验证**没有一张内置题目被重复发出**。


### 3.3 设计决策

**为什么沿用深血红而不是重做配色？**
原小程序的红色不是随便挑的：它同时承担了「亲密感」和「危险/刺激感」两种语义，
配合"心跳"这个母题。复刻版保留了色相，但把层次做深了——
加了 ECG 心电曲线背景、噪点颗粒、随抽卡强度起伏的心电振幅（`FX.excite()`）。

**字体**：没有用 Inter/Roboto 这类通用字体。正文用系统中文字体栈，
标题用**宋体/衬线**（`Songti SC` / `Source Han Serif`）——
中文衬线体自带一种"旧情书"的气质，比无衬线更贴合这个场景。
零外部字体请求，保证离线可用。

**动效克制**：只用三种——
① 视图切换的位移淡入（0.5s）；② 抽卡时的 `rotateY` 翻转 + 卡片白光；③ 心电曲线的持续呼吸。
没有一个"为了动而动"的装饰动画。
